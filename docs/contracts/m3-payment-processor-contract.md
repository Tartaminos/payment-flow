## M3-01 — Simulated PSP, request identity, financial outcomes

1. The simulated PSP is a **separate HTTP runtime/process in this repository**, run locally through a second IntelliJ run configuration on **port 8081** (PaymentFlow API local default **8080**). No real payment credentials. It stores idempotent external-effect decisions durably in a **separate PostgreSQL database named `paymentflow_psp_sim` on the existing local Docker PostgreSQL instance**, with its own Flyway migration history/DB credentials. It must not read or mutate PaymentFlow business tables; persistence remains independent even if both databases share the local learning container. Exact Java package/Maven module layout is the Architect's choice.
2. PSP simulator endpoints (internal, not client API): `POST /simulator/operations/authorize`, `GET /simulator/operations/{pspOperationId}`. Request contains `pspOperationId` = canonical `PaymentOperation.id` UUID, `amount` in minor units, `currency`, `merchantId`, and `paymentId`. Authentication is omitted **only for local simulation**. Never log credentials/cardholder fields.
3. **PSP idempotency:** unique `(merchantId, pspOperationId)` at the simulator. Same identity + identical type/amount/currency/payment parameters returns the **same persisted decision**; mismatched parameters return `409 PSP_OPERATION_CONFLICT`, never another financial effect. Concurrency is protected by PSP-side durable uniqueness. The simulator **persists its result before sending the HTTP reply** so tests can drop the reply after the effect.
4. Deterministic test fixtures control: **APPROVED** → `200` with `result=SUCCEEDED`; **DECLINED** → `200` with `result=REJECTED` and safe reason; **NON_EXECUTED** → `200` with `result=FAILED`, but **only** after authoritative no-effect evidence; **PROCESSING/UNKNOWN** → `202` or a status lookup reporting still unresolved. Fault fixtures can delay responses, drop a reply *after* committing the result, and return `503` without processing. Test-fixture control must be isolated from PaymentFlow's public API.
5. If no record is found by lookup, `404` means **not found at the lookup instant**, **not** affirmative proof that a prior request was never executed; do not translate lookup `404` into `FAILED` by itself. Definitive PSP decision identifiers/evidence are persisted and correlated with payment audit.
6. Payment Processor always loads the existing `PaymentOperation` and parent `Payment` from Postgres; Avro values identify work, **not authority** for amount/type/state. Kafka key `paymentId` must match the persisted parent; mismatched records never trigger PSP execution. `AUTHORIZE:SUCCEEDED` maps `Payment:AUTHORIZED`, explicit decline `AUTHORIZE:REJECTED` maps `Payment:DECLINED`. Proven technical non-execution is `AUTHORIZE:FAILED`, keeping Payment's last confirmed business status (initially CREATED). Every status change and audit append share one local DB transaction.

## M3-02 — Read-only Payment status API

- Approve **`GET /payments/{paymentId}`** using the same configured demo merchant; no new authentication model.
- `200`: `{paymentId, orderId, amount, currency, status, latestOperation:{operationId,type,status}}`. `latestOperation` denotes the most recently created PaymentOperation, sorted deterministically by created_at plus ID; no full history/pagination in MVP. Payment status and operation status are **separate** fields so `AUTHORIZE:UNKNOWN` leaves `Payment:CREATED`.
- Malformed/non-UUID ID → `400 INVALID_PAYMENT_ID`; unknown ID or wrong configured merchant → `404 PAYMENT_NOT_FOUND`. Do not change state or leak SQL/provider diagnostics.

## M3-03 — Safe attempts, active UNKNOWN recovery and abandoned PROCESSING

1. PSP financial calls are **at most 3 total attempts** per PaymentOperation with request deadlines **5s, 10s, 20s**. After a transient failure where the simulator explicitly **guarantees idempotency for the same operation identity**, optional retries use **1-second then 2-second fixed gaps** (separate from ADR-0009 Kafka backoff); definitive outcomes stop further attempts. Connection refusal before a request can be definitively classified as non-execution only if reliable evidence exists. Ambiguous timeout/read failure is **UNKNOWN unless safe retry/status lookup resolves it**.
2. Reserve/increment `attempt_count` **durably before** each outgoing financial request, never after; a crash after reservation conservatively consumes an attempt. Never reset the budget on Kafka redelivery, retry dispatch, restart or rebalance. Stable `pspOperationId` is the original PaymentOperation UUID.
3. Guard execution with a **DB conditional lease/ownership token** on the operation and exclusion for the same payment. Proposed processing lease **120s**, larger than the bounded 35s timeout total plus small gaps/margin; renewal or handoff must not allow competing PSP calls while an earlier owner's request can still be active. Expired PROCESSING claims require **PSP status lookup by original identity before any re-execution**; stale owner cannot commit state updates after lease ownership changed.
4. Introduce a small durable `reconciliation_jobs` table with **unique(operation_id)**, `unknown_since`, `next_check_at`, `lease_owner`, `lease_until`, `attempts`, `last_error`, `resolved_at`. On ambiguous outcome, **atomically commit Operation UNKNOWN, unchanged Payment confirmed state, audit event and reconciliation job**. A lost-response operation is NOT financially `FAILED`.
5. **Active independent recovery is in M3, not postponed to M6:** a separately scheduled logical scanner reads persisted due reconciliation jobs **without depending on original Kafka record replay**, runs `GET /simulator/operations/{pspOperationId}`, and safely resolves **AUTHORIZE** when definitive evidence arrives. This can be part of the same Spring Boot runtime but must operate independently of Kafka offset ownership, survive restart, use DB leases and retry persistent jobs. Proposed initial poll **every 5s**, bounded batch **20**, lookup HTTP timeout **3s**, next lookup delay **min(60s, 5s × 2^(failedLookups))**, no new financial POST. Provider still unknown → retain job/UNKNOWN. Later **M6-01 extends this path to CAPTURE/VOID** instead of constructing a second reconciling subsystem.
6. **Offset handoff invariant:** an UNKNOWN offset is eligible only after its job has committed and a **real functioning independent scanner/recovery workflow** exists. If scanner/recovery is not operational, withhold acknowledgment and surface unhealthy/backlog signal. Mere existence of a passive `UNKNOWN` row is insufficient. Reconciliation job admission and financial-state/audit append are atomic.

## M3-04 — Bounded workers and backpressure

- Main-topic topology remains **4 partitions / 1 active consumer group member / 4 async workers**. Define **global capacity = 32 total polled/in-flight records**, **at most 4 waiting records per payment** (excluding its active operation), **at most 8 polled/in-flight records per partition**. These are local educational defaults, not performance SLAs.
- Kafka poll thread never performs PSP HTTP. Set `enable.auto.commit=false` from **M3-01**. Baseline poll batch max **16 records**, worker completion tracked asynchronously; pause/resume assigned partitions on reaching admission limits while continuing polls/heartbeats to remain group member. Do not drop already-polled records or claim they are durable simply because enqueued.
- At most one locally active command per `paymentId`, per-payment FIFO; DB lease/state guards plus PSP stable idempotency protect cross-process/rebalance races. A command waiting locally because the payment is busy is **not** automatically a technical retry.
- Controlled shutdown/rebalance: stop new intake, fence revoked partition ownership, let bounded tasks finish or leave offsets uncommitted and recover by redelivery. A callback from an old generation must never commit offsets from new partition ownership. There is no in-memory queue persistence promise.

## M3-05 — Manual contiguous offsets and crash boundaries

- Source group **`paymentflow-processor-v1`**; poll-driven partition-aware tracker; commit Kafka next offset `N+1` **only when all earlier polled offsets in that partition are durably eligible**. Worker completions may finish out of order. Commit from consumer's owned poll thread (never directly from arbitrary worker threads), fenced by current assignment/generation.
- Eligible: definitively committed state+audit, verified already-terminal no-op, or `UNKNOWN` with **committed independent active reconciliation job and scanner**. Not eligible: in-memory work, ambiguous PSP result without job/scanner, abandoned PROCESSING without status check/recovery, or failed DB transaction.
- Crash after PSP effect but before DB commit: redelivery queries original PSP identity and/or uses persisted recovery job; never treats `PROCESSING` as proof of no prior external execution.
- No retry topic, DLQ publisher or capture/void in M3. Poison records cannot be silently skipped before M5: **withhold offset and surface a diagnosed blocked partition** (a known temporary operational limitation requiring M5 before full resilient consumer rollout).
- Tests: 4-partition out-of-order completion, worker crash, rebalance, repeated command, duplicate PSP reply loss, UNKNOWN committed only with active durable recovery, and no extra PSP effect.
